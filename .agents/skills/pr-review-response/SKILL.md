# レビュー対応

PR に付いたレビューコメントを取得し、コメントごとの修正と返信を対応一覧にまとめる。

- 対応一覧をユーザーが確認するまで、修正をコミットしない。指摘を確かめるための一時的な変更はしてよく、確かめたら戻す。
- push と返信の投稿は、ユーザーが指示したときだけ行う。
- 指摘は、コードで確かめてから受け入れる。誤っている指摘は、根拠を示して対応しない案にする。
- 提案された直し方より良い方法がある場合と、複数の案が挙げられている場合は、採る方法と理由を対応一覧と返信に書く。
- 意味が分からないコメントは、推測で直さず、質問する案にする。
- rebase と force-push はしない（[docs/PR_GUIDELINES.md](../../../docs/PR_GUIDELINES.md)）。

## 1. コメントを取得する

番号の指定がなければ、現在のブランチの PR を使う（`gh pr view --json number,url,title,author`）。

```shell
gh api graphql -F owner='{owner}' -F name='{repo}' -F number=<番号> -f query='
query($owner: String!, $name: String!, $number: Int!) {
  repository(owner: $owner, name: $name) {
    pullRequest(number: $number) {
      title
      url
      author { login }
      reviewThreads(first: 100) {
        pageInfo { hasNextPage endCursor }
        nodes {
          isResolved
          isOutdated
          path
          line
          originalLine
          comments(first: 50) {
            nodes { databaseId author { login } body url }
          }
        }
      }
      reviews(first: 50) {
        nodes { author { login } state body url }
      }
    }
  }
}'
```

- `hasNextPage` が `true` の場合は、`endCursor` を `after` に渡して残りを取得する。
- 対象は、`isResolved` が `false` で、最後のコメントが PR の作成者のものでないスレッドである。解決済みにしない運用のため、`isResolved` だけでは判断しない。
- `isOutdated` が `true` のスレッドは、指摘された箇所が現在のコードに残っているかを確かめる。`line` が `null` の場合は `originalLine` を使う。
- `reviews` の `body` に書かれた総評も読む。総評の中の指摘や問いは、対応一覧に載せる。

## 2. コメントごとに対応を決める

指摘された箇所と呼び出し元を読み、指摘が正しいかを確かめてから、次のいずれかに分ける。

| 対応           | 基準                                                             |
| -------------- | ---------------------------------------------------------------- |
| 修正する       | 指摘が正しい。同じ問題がこの PR のほかの箇所にあれば、併せて直す |
| 対応しない     | 指摘が現在のコードに当てはまらない、または Issue の対象外        |
| 質問する       | 意味が複数に読める、判断に必要な情報がない                       |
| 別の PR にする | この PR の目的から外れる。Issue の案を書く                       |
| 対応不要       | 良い点の指摘や補足で、返信がいらない                             |

コメントの先頭のバッジは、次のように扱う。

- `must`: 修正する。対応しない場合は、根拠が必要である。
- `imo`、`nits`: 直すかどうかを判断する。対応しない場合は、理由を返信に書く。
- `ask`: 質問に答える。答えがコードから読み取れない場合は、コードかコメントを直す修正を案にする。
- `next`: 別の PR にする。
- `good`、`memo`: 対応不要。

指摘されていない箇所の改善は、対応に含めない。

## 3. 対応一覧を示す

次の形式で示し、ユーザーの確認を待つ。ユーザーは番号で対応を変更できる。

```markdown
## レビュー対応一覧: #<番号> <タイトル>

| # | 種類 | 場所              | 指摘（要約） | 対応       | 修正内容 | 返信   |
| - | ---- | ----------------- | ------------ | ---------- | -------- | ------ |
| 1 | must | `<ファイル>:<行>` |              | 修正する   |          | <要点> |
| 2 | imo  | `<ファイル>:<行>` |              | 対応しない | —        | <根拠> |
| 3 | ask  | `<ファイル>:<行>` |              | 質問する   | —        | <質問> |

- 対応不要としたスレッド: <件数>
- 返答待ちのスレッド: <件数>
```

「返信」には、返信で伝える要点を書く。コミットの URL は、修正のあとに手順 5 で足す。指摘と違う直し方をする場合と、対応しない場合は、表の下に理由を書く。

## 4. 修正する

確認された「修正する」のコメントを、1 つずつ直す。

- 1 つのコメントにつき 1 コミットにする。
- commit message は [docs/COMMIT_CONVENTION.md](../../../docs/COMMIT_CONVENTION.md) に従い、この PR の既存のコミットに書き方を合わせる。
- コミットごとに、変更に関係する検査とテストを実行する。
- コミットの署名やフックが失敗した場合は、回避せずにユーザーに報告する。

## 5. 返信案を示す

対応一覧の「返信」をもとに、スレッドごとの返信案を示す。返信は敬体で書く。

- 修正した場合は、コミットの URL と、何を変えたかを 1〜2 文で書く。

  ```markdown
  https://github.com/<owner>/<repo>/pull/<番号>/commits/<40 桁の SHA> にて<何を変えたか>
  ```

  この URL は push のあとに開けるようになる。

- 確かめたことを書く場合は、実際に確かめたことだけを書く。
- 対応しない場合は、根拠をコードの引用かドキュメントで示す。
- お礼や同意だけの文は書かない。

## 6. push と返信の投稿

ユーザーが指示したら、push し、スレッドごとに返信を投稿する。PR 全体へのコメントではなく、スレッドに返信する。総評への返信だけは、PR へのコメントにする。`databaseId` は、スレッドの最初のコメントのものを使う。

```shell
gh api --method POST 'repos/{owner}/{repo}/pulls/<番号>/comments/<databaseId>/replies' -f body='<返信>'
```

スレッドは解決済みにしない。
