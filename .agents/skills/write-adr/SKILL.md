# ADR の作成と更新

決定を ADR に記録する価値があるかを判定し、記録する場合だけ ADR を作成または更新する。

ADR 以外の文書、コード、設定は変更しない。関連文書を読んで問題を見つけても、別の作業として報告する。

## 1. 運用ルールを読む

[docs/ADR.md](../../../docs/ADR.md) を読み、記録対象、書式、配置、更新方法に従う。

本スキルと `docs/ADR.md` が食い違う場合は、`docs/ADR.md` を優先する。

## 2. 依頼を整理する

会話と関連文書から、次を整理する。

- feature
- 決定
- コンテキスト（背景・課題・制約）
- 検討した代替案と棄却理由
- 影響（メリット・デメリット・補う工夫・新たな制約）
- 関連する要件定義書、設計書、規約、コード

会話にない内容を推測で補わない。決定が未確定の場合は ADR を作らず、設計中の文書または Issue で決定してから再度依頼するよう伝える。

## 3. 記録の可否を判定する

次のいずれかを判定する。

### 記録する

[docs/ADR.md](../../../docs/ADR.md) の「記録する決定」を満たし、決定と理由を根拠から確認できる。

### 記録しない

次のいずれかに該当する。

- 未決定の提案
- コード・仕様・規約から理由が分かる判断
- 選択肢がなかった判断
- 誰が見ても採用する方式が明らかな判断
- 一般論で答えられる判断
- 作業の経緯や実装状況
- ADR に書くほどではない小さな理由

ファイルを変更せず、記録しない理由を伝えて終了する。記録しない判定はエラーとして扱わない。

### 情報不足

記録対象ではあるが、決定、根拠、代替案の棄却理由、または影響に必要な情報を確認できない。

ファイルを変更せず、不足している情報と確認先を伝えて終了する。根拠のない文章を作って書式を埋めない。

## 4. 根拠を確認する

依頼内容だけを信用せず、関連する要件定義書、設計書、規約、コードを読む。

ADR に書く各文が、会話または確認した文書のどこに基づくかを確かめる。特に次を確認する。

- 決定は人が合意した内容か
- 根拠は実際に述べられたものか
- 代替案の棄却理由に、その判断が依存する前提があるか
- 影響は根拠から確認できるか

要件にない設計を例外的に採用するなど、承認の事実自体が根拠になる場合は、承認者の発言を改変せず引用する。なぜ通常の要件や設計へ戻せないかを確認できなければ、情報不足とする。

## 5. 記載先を決める

`docs/adr/ADR-*_{feature}.md` を検索する。

- 1 ファイルある: そのファイルを更新する
- ない: 成果物 ID の規則で割り当てられた未使用の `ADR-{NNN}` を確認し、`docs/adr/ADR-{NNN}_{feature}.md` を作る
- 複数ある: 同じ feature の ADR が分かれている問題を報告し、変更せず終了する

成果物 ID の採番方法が決まっていない、ID が割り当てられていない、または重複している場合は情報不足とする。手動で推測して採番しない。

複数の feature にまたがる決定は `common` に記録する。

## 6. ADR を記載する

### 新しい決定

ADR ファイルがなければ、[template/ADR_TEMPLATE.md](template/ADR_TEMPLATE.md) を読み、プレースホルダを決定内容へ置き換えて作成する。テンプレートにない見出しやメタデータを追加しない。

既存ファイルへ追加する場合は、末尾に新しい決定の節を追加する。節番号は既存の最大値に 1 を足す。

### 既存の決定の変更

対象の決定の節を現在の内容へ書き直す。

1. 「決定」を新しい内容と根拠へ変更する
2. 旧い決定を「検討した代替案」へ移す
3. 旧い決定を採用しなくなった理由を書く

旧い根拠が誤りだった場合は、誤った根拠を残さない。前提が変わった場合は、当時は妥当だったことと、変わった前提を書く。

別の節や別の ADR を追加して置き換えを表さない。「失効」などの Status を付けない。節番号を変更・削除・再採番しない。

## 7. 検証する

記載後に次を確認し、問題があれば修正する。

- 変更したファイルは対象の ADR だけである
- 各決定に「コンテキスト」「決定」「検討した代替案」「影響」がある
- 各文に根拠があり、推測で補った内容がない
- 1 つの決定の節だけで内容を理解できる
- 節番号を変更・削除・再採番していない
- 必要な参照に、到達可能な Markdown リンクがある
- 調査内容、議論の経緯、実装手順、変更対象ファイル一覧、Status 履歴が混入していない

## 8. 結果を伝える

- **記録した**: ADR のパスと、作成または更新した決定の節を示す
- **記録しない**: 理由を示す
- **情報不足**: 不足している情報と、何を確認すれば再度依頼できるかを示す

ADR の作成・更新後は、作成者とは別の観点でレビューするよう案内する。コミットや push は、依頼されない限り行わない。
