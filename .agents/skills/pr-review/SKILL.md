# PR の差分レビュー

PR の差分をレビューし、変更行へのコメントと総評を 1 つのレビューとして投稿する。

- Approve とマージはしない。投稿するレビューは `COMMENT` にする。`REQUEST_CHANGES` にするのは、ユーザーが指示したときだけである。
- PR 本文と commit message はレビューしない。作成者の意図を知るために読む。作成者が確認済みと書いたことを自分で確かめていない場合は、確かめていないこととして書く。
- 指摘は、確かめてから書く。読んで問題だと思っても、実行して確かめるか、根拠になるソースやドキュメントを示す。確かめきれない懸念は、断定せず `ask` で尋ねる。
- PR のブランチには何も push しない。確かめるための変更は手元で行い、コミットしない。
- コメントと総評をユーザーが確認する前に、投稿しない。

## 1. 対象を取得する

```shell
gh pr view <番号> --json number,title,body,state,isDraft,baseRefName,headRefOid,closingIssuesReferences,files
gh pr diff <番号>
```

- `state` が `OPEN` でない場合、または差分が空の場合は、その旨を伝えて終了する。
- PR 本文の「レビュー観点」に対象外が書かれていれば、その範囲はレビューしない。問いが書かれていれば、確かめて総評で答える。
- `closingIssuesReferences` に Issue があれば、完了条件や期待される動作を読む。
- PR 本文の「レビューレベル」で選ばれたレベルに、確かめる深さを合わせる。選ばれていない場合は Lv2 とする。

  | レベル | 確かめる深さ                                                                           |
  | ------ | -------------------------------------------------------------------------------------- |
  | Lv1    | 差分を読む。実行はしない。読んで気づいた懸念は `ask` で尋ねる                          |
  | Lv2    | テストを実行し、変更を元に戻すと落ちるかを確かめる。テストがない変更は、手元で実行する |
  | Lv3    | Lv2 に加え、実行環境で動作を確かめる。できない場合は、確かめていないこととして書く     |

- Lv2 と Lv3 で実行して確かめる場合は、作業中のブランチを切り替えず、別の作業ツリーに取り込む。

  ```shell
  git fetch origin pull/<番号>/head
  git worktree add --detach <リポジトリの外のディレクトリ> FETCH_HEAD
  ```

  依存は、その作業ツリーで `flutter pub get` を実行して取得する。ステージやコミットを伴う確認は、使い捨ての複製で行う。

## 2. レビューする

変更行の前後だけで判断できない場合は、ファイル全体と呼び出し元を読む。次の順に確かめる。

1. 正しさ。変更が意図どおりに動くか。動かない入力や環境がないか。
2. Issue との対応。完了条件のうち実装されていないもの、Issue にない変更。
3. テスト。変更を元に戻すと落ちるテストがあるか。
4. アーキテクチャ。パッケージ間の import や依存が変わる場合は、[docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md) の依存の向きとレイヤーの責務に照らす。
5. 連動する変更。生成コード、`apps/catalog/`、ドキュメント、CI の更新漏れ。

## 3. コメントを絞る

書いたコメントを見直し、次のいずれかに当てはまるものは捨てる。指摘が残らなければ 0 件でよい。

- 変更されていない行へのコメント。Issue の完了条件の未実装のように、変更行に結び付かない指摘は総評に書く
- この PR より前からある問題。この PR の変更で表に出る場合は残す
- formatter と linter が検出するもの
- 好みの違い

1 つの問題につき 1 コメントにする。同じ問題が複数箇所にある場合は、最初の箇所にコメントし、ほかの箇所を本文に列挙する。

## 4. コメントを書く

コメントの先頭に、種類を示すバッジを付ける。コメントと総評は敬体で書く。

| 種類   | 意味                                                         | バッジ                                                                    |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `must` | 意図どおりに動かない場合がある、Issue の要件を満たしていない | `![must-badge](https://img.shields.io/badge/review-must-red.svg)`         |
| `imo`  | 直したほうがよいが、判断は作成者に任せる                     | `![imo-badge](https://img.shields.io/badge/review-imo-skyblue.svg)`       |
| `nits` | 細かい指摘                                                   | `![nits-badge](https://img.shields.io/badge/review-nits-orange.svg)`      |
| `ask`  | 意図の確認、確かめきれない懸念                               | `![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg)`   |
| `next` | 別の PR で対応すればよい                                     | `![next-badge](https://img.shields.io/badge/review-next-blueviolet)`      |
| `good` | 良い点                                                       | `![good-badge](https://img.shields.io/badge/review-good-blightgreen.svg)` |

````markdown
![imo-badge](https://img.shields.io/badge/review-imo-skyblue.svg)

<してほしいことを 1 文で>

<理由。何をどう確かめたか。根拠のリンク>

```suggestion
<その変更だけで問題が解消する場合に限って付ける>
```
````

- `suggestion` にできない修正案（別のファイルへの追加など）は、通常のコードブロックで示す。
- テストの不足は、守られていない実装の行に付ける。
- `good` は、判断や工夫を具体的に述べられる場合だけ付ける。指摘の件数には数えない。
- コードについて書き、作成者については書かない。「〜していません」ではなく「この行は〜になっています」と書く。

## 5. ユーザーに確認する

コメントと総評を示し、確認を待つ。指摘が 0 件の場合は、表を省いて「指摘はありません」と書き、総評を示す。

```markdown
## レビュー結果: #<番号> <タイトル>

| # | 種類 | 場所              | 内容      |
| - | ---- | ----------------- | --------- |
| 1 | must | `<ファイル>:<行>` | <1〜2 文> |

### 1. `<ファイル>:<行>`

<コメントの全文>

### 総評

<下の形式>
```

総評は次の形式にする。

```markdown
![memo-badge](https://img.shields.io/badge/review-memo-lightgrey)

<レビューの結論を 1〜2 文で。must があるかどうか。どのレビューレベルで確かめたか>

## 確かめたこと

- <読んだもの、実行したものと、その結果>
- <レビュー観点の問いへの答え>

## 確かめていないこと

- <実機での動作など>
```

## 6. 投稿する

確認されたコメントと総評を、1 つのレビューとして投稿し、レビューの URL を示す。

```shell
gh api --method POST 'repos/{owner}/{repo}/pulls/<番号>/reviews' --input <JSON ファイル>
```

```json
{
  "commit_id": "<headRefOid>",
  "event": "COMMENT",
  "body": "<総評>",
  "comments": [
    {
      "path": "<ファイルパス>",
      "line": 42,
      "side": "RIGHT",
      "body": "<コメント>"
    }
  ]
}
```

- 追加・変更後の行は `side` を `RIGHT`、削除された行は `LEFT` にする。
- 複数行にコメントする場合は `start_line` と `line` を指定し、`start_side` を `side` と同じ値にする。
- `event` は `COMMENT` にする。ユーザーが指示した場合だけ `REQUEST_CHANGES` にする。`APPROVE` にはしない。

## 7. 片付ける

手元の変更を元に戻し、作った作業ツリー、複製、JSON ファイルを削除する。
