# 不具合の原因と影響範囲の調査

不具合の原因と、修正がどこまで波及するかを調べ、結果を Issue にコメントする。

- 修正はしない。調査のためのコードの変更（ログの追加、再現用のテスト、Issue に書かれた修正案の試し）は手元で行ってよい。コミットと push はしない。
- Issue に書かれた原因、修正案、予想される結果は、確かめるまで仮説として扱う。読んで納得しても、実行して確かめる。
- 原因を証拠で示せるまで、修正方針を書かない。確かめていないことは、未確認と書く。

## 1. 症状を確かめる

```shell
gh issue view <番号> --json title,body,labels,comments
```

- 期待される動作の根拠（ドキュメント、テスト）を探す。根拠が Issue の記述だけの場合は、報告にそう書く。
- Issue が書かれたあとに状況が変わっていないかを確かめる（以降の実行記録、関係するファイルや設定の変更）。
- 症状が複数ある場合は、症状ごとに分けて進める。
- 調査中に Issue にない症状を見つけたら、結論に 1 行で書く。深く調べるかは、ユーザーに尋ねる。

## 2. 再現する

対象に合った手段で再現する。

| 対象                         | 手段                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| Dart / Flutter のコード      | 対象のパッケージのディレクトリでテストを実行する。なければ、再現用のテストを `test/` に書く |
| ワークフロー                 | 失敗した実行のログを読む（`gh run view <ID> --log`）。再実行はユーザーに確認してから行う    |
| composite action、スクリプト | 同じイメージとシェルで、該当するステップだけを手元で実行する                                |

コンテナの起動やイメージの取得のように手元の環境を変える手段は、使う前にユーザーに確認する。

- テストは、Flutter に依存するパッケージでは `flutter test`、それ以外では `dart test` で実行する。`melos exec --scope` は使わない。パッケージ名がディレクトリ名と異なり、一致しなくても成功と表示される。
- 再現用のテストは、期待される動作を期待値にし、現状では失敗するものにする。
- 症状を起こせたが、結果が Issue の予想と違った場合は、未再現とはせず、実際の動作を症状として書く。
- 症状を起こせなかった場合は「未再現」とし、原因の候補と確認方法、再現に必要な情報を報告する。修正方針は書かないが、Issue の修正案を試した結果は書いてよい。

## 3. 原因を特定する

- 同じ種類の処理で正しく動いているものがあれば、差分を挙げる。
- SDK、依存パッケージ、外部の action の挙動が関係する場合は、固定されたバージョンのソースを読む。ソースが読めないサービスの挙動は、公式ドキュメントを証拠にする。
- レイヤーをまたぐ場合は、[docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md) の依存の向きに沿って、どの境界で値が期待から外れるかを特定する。

原因がどこにあるかを分ける。

| 原因   | 判断の基準                                                            |
| ------ | --------------------------------------------------------------------- |
| 実装   | 期待される動作は明確で、コードがそれと異なる                          |
| 仕様   | コードは Issue やドキュメントの記述どおりで、記述が誤り・未定義・矛盾 |
| テスト | テストがない、誤った期待値を固定している、CI で実行されない           |
| 設定   | コードも仕様も正しく、リポジトリや外部サービスの設定が足りない        |

原因が仕様にある場合、どの挙動が正しいかは決めず、選択肢を示してユーザーに判断を求める。

## 4. 影響範囲を調べる

- 修正で変更するシンボルの参照元を `git grep -n` で探す。private なシンボルは、それを使う公開シンボルの参照元までたどる。
- 同じ原因で壊れるほかの箇所を探す（同じファイル、同じシークレット、同じ条件を前提にするもの）。
- 連動して変わるものを確かめる。生成コード、テストと golden テスト、`apps/catalog/`、`pubspec.yaml` の依存、呼び出し元のワークフロー、ドキュメント。
- 探した範囲と、探していない範囲を記録する。

## 5. 報告する

報告を書き、ユーザーに示す。調査の経緯を知らない人が読む前提で書く。

- 先頭に結論を書く。症状ごとに 2 文まで。
- 原因は、該当するコードを数行引用し、コミットを固定したリンクを添える。リンクのコミットは push 済みのものを使う。

  ```shell
  echo "$(gh repo view --json url --jq .url)/blob/$(git rev-parse HEAD)/<ファイルパス>#L<開始行>-L<終了行>"
  ```

- ファイル名を省いた `:74` や「同上」のように、内容を省くための参照は書かない。
- 手順 3 の表の語ではなく、「コードの誤り」「仕様が未定義」のように書く。
- 影響範囲は、変更が必要なものと、判断が必要なものだけを書く。変更が不要なものは記録に入れる。
- 修正は文章で書き、推奨を 1 つ示す。別案がある場合だけ、案ごとの利点と欠点を書く。
- 記録は末尾の `<details>` にまとめ、結論の根拠になるコマンドと出力に絞る。記録は 40 行を目安にする。

````markdown
## 結論

1. **<症状の要約>**: <原因>。<推奨する修正>。
2. **<症状の要約>**: 未再現。<分かったこと>。

## 1. <症状の要約>

<原因を 1〜3 文で>

```<言語>
<該当するコード。数行>
```

<コミットを固定したリンク>

**修正**: <推奨する修正と、その理由>

**併せて必要な変更**: <なければ書かない>

**判断が必要**: <なければ書かない>

**未確認**: <なければ書かない>

## 2. <症状の要約>

未再現。<試したことと、分かったこと>

**原因の候補**: <候補と、その確認方法>

**再現に必要な情報**: <端末、OS、手順など>

<details>
<summary>再現と調査の記録</summary>

<環境、実行したコマンドと出力、探した範囲、探していない範囲>

</details>
````

示す前に、次を確かめる。

- 結論だけを読んで、原因と次にすることが分かる。
- 引用したコードと、リンクの行が一致している。
- 確かめていないことを、確かめたように書いていない。報告に書いたコマンドや修正は、実際に試した形と同じである。

## 6. Issue にコメントする

ユーザーが報告を確認したら、Issue に投稿し、コメントの URL を示す。Issue 番号がない場合は投稿しない。

```shell
gh issue comment <番号> --body-file <報告のファイル>
```

## 7. 片付ける

`git status` で調査用の変更を確かめ、元に戻す。`git stash` は使わない。リポジトリの外に作ったファイル、起動したコンテナも片付ける。再現用のテストのように修正で使えるものは、戻す前に残すかをユーザーに尋ねる。
