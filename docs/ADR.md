# ADR 運用ルール

このドキュメントでは、ADR（Architecture Decision Record）へ記録する内容と、作成・更新・参照のルールを説明します。

ADR は設計書ではありません。設計書に記載した設計をなぜ選んだかと、見送った代替案を将来再検討できるように残す決定記録です。

## 文書の責務

- **設計中の文書と Issue**: 未決定の案、比較検討、調査内容、議論の経緯を扱う
- **設計書**: 決定後の現在の設計を、仕様の正式な内容として扱う
- **ADR**: 設計書に記載した設計を選んだ理由と、見送った代替案の棄却理由を扱う
- **git 履歴**: 決定日、変更日、過去の記述を扱う

未決定の案を ADR にも書くと、設計中の文書や Issue と責務が重複し、人や AI が提案を決定事項として参照する危険があります。そのため、ADR は決定後にだけ作成します。

## 記録する決定

次の両方を満たす決定を記録します。

1. 将来、もっともらしい代替案が再提案される可能性がある
2. コード・仕様・規約を読んでも、その代替案を採用しなかった理由が分からない

次の内容は記録しません。

- 未決定の提案
- コード・仕様・規約から理由が分かる判断
- 選択肢がなかった判断
- 誰が見ても採用する方式が明らかな判断
- 一般論で答えられる判断
- 作業の経緯や実装状況
- ADR に書くほどではない小さな理由

不要な決定を増やすと、将来の読み手が必要な決定を探せなくなります。記録しない判定はエラーではありません。

## 配置とファイル

ADR は `docs/adr/` に配置します。

同じ feature の決定は、次の名前の 1 ファイルへまとめます。

```text
docs/adr/ADR-{NNN}_{feature}.md
```

- `ADR-{NNN}` は成果物 ID です。採番方法は、成果物 ID の規則に従います
- `{feature}` は小文字の英数字と `_` を使います
- 複数の feature にまたがる決定は `common` に記録します
- 同じ feature の ADR が既にある場合、新しいファイルを作らず、そのファイルへ決定を追加します
- 成果物 ID の採番方法が決まっていない場合、新しい ADR ファイルは作成しません

## ファイルの構成

ファイルには、タイトルと決定の節だけを記載します。新しいファイルは [ADR テンプレート]を使って作成します。

決定を追加するときは、末尾に `## 2.`、`## 3.` のように節を追加します。各決定の節は、それだけを読んでも内容を理解できるようにします。

節番号は、外部から `ADR-{NNN} §1` のように参照する識別子です。一度付けた節番号は変更・削除・再採番しません。

## 書かない内容

ADR は決定と理由に絞り、次の内容を書きません。

- 調査内容
- 議論の経緯や時系列
- 実装手順
- 変更対象ファイルの一覧
- 仕様や規約の複製
- 日付や Status の履歴

仕様や規約の正式な内容は元の文書へ記載し、ADR から参照します。

## Status

ADR は決定後にだけ作成するため、Status 欄を持ちません。

- ADR の「決定」に書かれた内容は採用済みです
- 見送った案は「検討した代替案」に棄却理由とともに記載します
- 決定の変更は、同じ決定の節を更新して表します
- 日付と変更履歴は git 履歴で確認します

## 決定を変更する

既存の決定を変更するときは、新しい節や別の ADR を追加せず、対象の節を現在の決定へ更新します。

1. 「決定」を新しい内容と根拠へ書き換える
2. 旧い決定を「検討した代替案」へ移す
3. 旧い決定を採用しなくなった理由を書く

旧い根拠が誤りだった場合は、誤った根拠を残さず、正しい理由へ置き換えます。前提が変わった場合は、当時は妥当だったことと、変わった前提を記載します。

「失効」などの印だけを付けたり、旧い決定を残したまま別の ADR を追加したりしません。現在有効な決定を一箇所で読める状態に保ちます。

## 参照

設計書、コード、テストなどから ADR を参照するときは、成果物 ID と決定の節を記載します。

```markdown
[ADR-{NNN} §1](相対パス#1-決定のタイトル)
```

ID だけでは参照先へ到達できないため、内容を読む必要がある参照には Markdown リンクを付けます。ADR から仕様や規約を参照するときも、相対パスの Markdown リンクを使います。

## 決定者と決定日

決定者と決定日は通常、ADR 本文へ記載せず、git と Issue の履歴で確認します。

要件にない設計を例外的に採用するなど、承認の事実自体が決定の根拠になる場合は、承認者の発言を改変せず引用し、なぜ通常の要件や設計へ戻せないかを記載します。

## 作成・更新

ADR の作成と更新には、`write-adr` スキルを使います。

スキルは次の結果のいずれかを返します。

- **記録する**: ADR を作成または更新する
- **記録しない**: ADR の記録対象ではないため、ファイルを変更しない
- **情報不足**: 根拠が不足しているため、ファイルを変更せず、必要な情報を示す

作成・更新時は、次を守ります。

- 依頼内容だけを信用せず、関連する要件定義書・設計書・規約・コードを確認する
- 決定、根拠、代替案の棄却理由、影響に根拠があることを確認する
- 根拠のない内容を AI が推測で補わない
- 対象の ADR ファイル以外を同時に変更しない
- 作成・更新後に、必須項目、節番号、参照リンクを検証する
- 作成者とは別の観点で ADR をレビューする
